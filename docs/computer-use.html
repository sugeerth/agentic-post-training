The parser was the problem

A hand-written font matcher recovered every label from the pixels and handed the policy a clean string. Three encodings built on it all scored below chance, with attention spread flat across the screen. Deleting it — making the model read the rendered glyphs instead — more than doubled grounding and produced the first evidence the model attends to anything at all.

Text encoding — twelve tokens per caption

A caption arrives already decoded: <c:S> <c:U> <c:B>…, matched glyph by glyph against the renderer's 3×5 bitmaps. That matcher is the most elaborate hand-written component in the package and it recovers 271 of 271 labels correctly.

Vision encoding — one slot of 144 numbers

The same captions, as actual pixels. Nothing decodes them. To ground an instruction the model must associate stroke shapes with the instruction's own characters.

What this does not say

Vision does not clear the chance floor. The point estimate 34.4% is above the 31.2% a policy picking uniformly among on-screen controls would get, but its lower bound is 25.5% — chance is not excluded at 95%. The finding is that vision beats text, where the intervals are disjoint, not that the policy is good.

The 47.3% label-overlap heuristic is not a bar here. It reads labels out of the context, and the vision encoding has none. That heuristic was always exploiting the parser's transcription — exactly what this run ablates.

Four encodings, one ratio that moved

Of the attention reaching the screen, how much lands on the control the instruction named — against what an even spread would give.

The premise of the encoding is that emitting a click is a copy: find the label the instruction names, take the cell beside it. Three text encodings sat at 1.01, 1.10 and 0.99 — the model spreading its gaze flat and emitting a coordinate anyway, which is why each scored at or below chance however the answer was written down.

Set-of-marks came from the GUI-grounding literature and predicted a rise. It did not happen. Pixels took the ratio to 1.18 — the first time the mechanism the encoding assumes has shown up in the measurement.

Serving it

The sampling half of post-training: rollout generation, not the gradient step, is where the wall clock goes.

Bit-identical, and 6.1× faster

Keys and values computed once per position instead of once per emitted token, with no autograd graph on a path that never calls backward(). 214/214 logits identical to the trainer, maximum difference exactly zero — now including a model with an image in the sequence.

That standard is not fussiness. A sampler that merely rounds differently from its trainer draws from a policy the trainer never had: the loss still falls, the reward still rises, and nothing fails.

A cache bug with no symptom

A placeholder token is the same token whatever image stands behind it. Two requests showing different screens can carry byte-identical ids — and a cache keyed on ids alone serves the first screen's keys and values for the second one's request. Nothing raises. The model answers about a frame it was never shown.

Keys are now (token id, content digest). Same screen reuses everything; a different screen reuses nothing.

What did not work

Reported at the same length as what did.

RL post-training: 20.4% → 19.4%

GRPO on verified rollouts, warm-started from the SFT checkpoint. Within noise, and 29% of groups were unanimous and carried no gradient at all.

Running it from a random init first was the useful failure: reward stayed negative every round because ~90% of samples did not decode and none matched gold. GRPO needs a non-zero pass rate to have a gradient to climb. Post-training is post for a reason.

Two flaws in the instrumentation

Each round scored a different random subset, so the reward series was not comparable across rounds — a trend line drawn through points that partly measured the sampler. And the loop returned its final checkpoint, which was its worst: round 4 scored 0.390, round 5 scored 0.138, and round 5 is what got evaluated.

Both fixed — a fixed probe scored identically every round, and best-round tracking. Neither rescues the result.

Verified, and not

Runs in CI with no GPU: the inference runtime, prefix cache, versioning and batch assembly; the diagnostic instrument; the RL loop; every training run and every number on this page. ruff clean, mypy --strict across 41 files.

Not verified: torch is absent in that environment, so GRPOTechnique.step() cannot take its real path — the batch is checked for shape, not consumption. The vLLM and SGLang engines behind the same protocol have not been run. And n=93 is small: every interval here is wide, and the headline result is disjoint from its baseline by six tenths of a point.
